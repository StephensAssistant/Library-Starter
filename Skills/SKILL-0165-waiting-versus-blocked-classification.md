# Waiting-versus-Blocked Classification

Classify stalled or externally dependent work accurately.

## When to use

Use when the next outcome depends on a person, source, decision, access or constraint.

## Method

1. Name the required next outcome.
2. Identify the person, system, source or constraint governing it.
3. Classify waiting when a named external input is pending within an understood route.
4. Classify blocked when no required next outcome can progress until a constraint is resolved.
5. Record the evidence, owner, next chase or resolution action and review point.
6. Reassess when the dependency state changes.

## Decision and evidence details

Apply the state to the named outcome and current scope, not every open item collectively. Record which other authorised work can progress and which acceptance remains dependent. If the external route, required input or actual constraint is unverified, report the classification gap rather than selecting a convenient state.

Boundary design case: a vendor is silent and nobody can establish the request route. Do not call this understood waiting; identify the missing route/owner evidence before classification.

## Benchmark case

A vendor response is pending through a verified route, with a named owner and review action, and no unresolved intervention constraint blocks the scoped next outcome. Record waiting for that input. Assess any prevented execution or final acceptance separately; unrelated planned work continuing does not prove the required outcome is unblocked.

## Anti-patterns

- Calling every external wait blocked.
- Hiding a genuine execution constraint as waiting.
- Leaving the dependency unnamed.

## Stop

Stop with an evidenced state and actionable review or resolution path.
