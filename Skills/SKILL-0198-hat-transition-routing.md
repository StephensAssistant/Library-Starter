# Hat Transition Routing

Switches Hats when work crosses a role, expertise, independence or authority boundary.

## When to use

Use during mixed work when the active action no longer belongs to the current Hat.

## Method

1. Decompose mixed work into action units.
2. Use the smallest complete Hat sequence.
3. Switch when owner, expertise, independence or decision authority changes.
4. Carry forward only objective, checked facts, constraints, current artifact and next action.
5. Load every confirmed associated asset; do not omit one because routing confidence is below 95%.

## Decision and evidence details

Retain the action boundary, outgoing checked facts and artifact revision, incoming responsibility and required authority. Switching reasoning roles does not create a second actor or independent acceptance; use the governing review contract for that evidence.

Boundary design case: the author changes to a Validator Hat to review their own implementation. Record the self-check accurately and keep any required non-author review pending. A named Hat cannot supply missing independence or execution permission.

## Benchmark case

An email, document and script route through communication, documentation and engineering Hats with concise checked handoffs.

## Anti-patterns

- One Hat for all actions
- Ceremonial switching without boundary change
- Omitting confirmed associations

## Stop

Stop when the current action has the correct Hat and a checked handoff from the prior action.
