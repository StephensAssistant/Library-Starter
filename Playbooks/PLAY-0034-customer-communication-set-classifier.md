# Business Communication — Classifier and Structure

## Trigger

A business communication is requested or authorised work needs a draft. Business is the default context unless the Library owner explicitly states that it is personal.

## Method

Read current state and classify the communication by audience, channel, purpose, sensitivity, required outcome, owner, deadline and approvals. Select the closest structure below, combining compatible purposes when useful. Draft one concise, human message using STAR substance—Situation, Task, Action, Result—without forced headings or robotic phrasing. For unfinished work, Result is the current outcome, blocker or next action; never imply completion. Return a send-ready draft labelled with audience, channel, subject, purpose and any required approval. the Library owner explicitly reviews and sends or posts it; the AI never sends. Record changed waiting or acceptance state only after the Library owner confirms the communication occurred.

## Stop

Send-ready draft delivered. Never send, schedule or publish; never mark drafted as sent, silence as acceptance, or start an automatic chase schedule.

AGENTS.md owns shared authority, evidence reuse and task boundaries.

## Communication structures

- **Acknowledgement/intake:** reference; concise understanding; ownership; immediate next step; no unverified promise.
- **Information request:** known context; exact missing fact; why it matters; requested action; real deadline only when evidenced.
- **Follow-up/chase:** original request and date; what remains outstanding; impact; requested response; agreed review point if one exists.
- **Status/progress:** current headline; completed action and evidence; present impact/state; blocker or risk; next action, owner and evidenced date.
- **Incident/data awareness:** affected service, metric or report; confirmed facts versus suspected impact; affected window; safe-use guidance; investigation underway; next update point when known.
- **Resolution:** resolved outcome; affected window; corrective action at an appropriate level; verification evidence; any user action; thanks/closure.
- **False alert/no defect:** reported concern; checks performed; evidence-based explanation; confirmation no defect was found; interpretation guidance.
- **Escalation/access blocker:** issue; evidence; business impact; action or authority required; identified owner; evidenced deadline or waiting status.
- **Acceptance/sign-off:** delivery; acceptance criteria; validation evidence; explicit decision requested; remaining limitations or open items.
- **Closure:** original need; delivered result; verification/acceptance; residual action if any; clear close statement without implying unconfirmed acceptance.
- **Waiting/handoff:** current state; completed stages; exact dependency; waiting party; last action; next review/chase point if known; next executable action.
- **Meeting:** decision/outcome sought; essential context/pre-read; minimal agenda; afterwards, decisions, owners, actions and dates.
- **Change/CAB:** reason; scope; impact; risk; validation; rollback/fix-forward approach; window and approvals only when evidenced.

If no structure matches, use the universal minimum: audience outcome; verified situation; task or decision; action taken/requested; current result; owner; next action/date; sensitivity and approvals. A new scenario may extend this list only from repeated, verified need—not speculation.

## Output contract

Return a send-ready draft with audience, channel, purpose, sensitivity and approval status established from the request or record. Format the user-facing draft by channel: a new email receives a subject plus paste-ready body; an email reply receives the paste-ready body only unless the Library owner requests a changed subject; Freshservice, Teams and similar channels receive a paste-ready message body only. Keep operational labels outside the text the Library owner will paste. Emails use a natural greeting and sign-off appropriate to the relationship and thread; Freshservice, Teams and similar conversational channels omit them by default unless the existing conversation style requires them. Separate facts, interpretation, risk and request. Use the audience's terminology and reference. the Library owner reviews and sends or posts every communication.

## Open decision

- Channel selection when unstated: infer from the authoritative work record and ask only when ambiguous, or always ask the Library owner. Do not silently adopt either rule until the Library owner decides.
