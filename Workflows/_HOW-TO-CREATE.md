# Create or revise a Workflow

1. Read AGENTS.md once for this task, then Workflows/README.md and the existing owner, used plan and relevant sources. Search Workflows, Playbooks and Skills before creating.
2. Apply HAT-0023 for workflow lifecycle expertise, with HAT-0022, SKILL-0313 and SKILL-0318. Director returns specialist requirements to HAT-0001; Head Librarian makes assignments and coordinates their work. Use PLAY-0069 outside the target workflow for first qualification, failed admission and recorded repair routes. Settle consequential design decisions with the Library owner before dependent work. Define the outcome, scope, acceptance, authority and gap ownership. Under AGENTS rule6 an explicit invocation of an already-approved graph may cover its declared components, including PLAY-0056, without repeated component exception prompts; source construction/review is not invocation. Test inherited scope, actual call membership, access, stopped-child denial, shared bounds and fresh candidate-baseline handoff; merge and other excluded actions keep separate authority.
3. Reserve FLOW through the serialised ID workflow only when a new record is needed. Copy _TEMPLATE.md; use the returned ID. No allocation is needed to revise an existing record.
4. Build one explicit workflow-json graph and human-readable scope. Bind every step/control state to an available governing Playbook and build requirement-to-Skill coverage from actual contracts. An executable step uses its bound Playbook; nested calls and control states also remain governed by a Playbook. Reuse existing Playbooks/Skills/Hats. Add only confirmed direct references to links and update their reciprocal endpoints in the same final source pack. Do not infer relationships from similarity.
5. Resolve any missing/incomplete supporting Playbook or Skill through search, reuse, amendment or justified governed creation; eliminate material ambiguity and recheck affected callers. No available Playbook means keep that proposed step in the work Ticket/plan until one exists, without guessed IDs. Include the correct supporting Skills in declared executable dependencies and confirmed reciprocal canonical associations. Record requirement/step coverage, current hashed verification evidence and gaps. Keep status current and review_status draft or needs_review while findings, evidence or dependencies remain incomplete. Preserve historical approvals with their original scope; never treat them as the current receipt.
6. Separate immutable qualification evidence from the mutable run/work owner. Establish the expected runtime write footprint and prove a normal owner/used-plan checkpoint preserves admission. Refuse overlap with all frozen controls and test/coverage/review proof, including called workflows; use the read-only --planned-write preflight. Test normal, failure and boundary scenarios; add relevant stale-state, denied action, partial failure, retry, recovery and authority cases. Capture actual setup/results in the work owner or governed evidence files. Do not fabricate PASS or future runtime proof.
7. Build transitive instruction/policy pins from the actual final bytes. Have Director and a separate reviewer map the actual conditional native/resource/import union into .github/workflow-resources.json for this FLOW; hash exactly that set in resource_pins, excluding mutable run inputs. The registry is itself policy-pinned. A separate non-author reviewer verifies fitness, complete requirement-to-Playbook-to-Skill coverage, material ambiguity, gaps, test evidence and dependency changes. On correction, rerun affected checks and obtain updated review. Only that exact reviewed definition may become approved. After any dependency/policy/resource change, rebuild affected workflows bottom-up in the same repair—independently re-review the changed unsigned definition, refresh its review fingerprint and evidence, compute the final whole-file SHA-256, update each downstream workflow pin to that final digest, and repeat through callers until full `check_workflows.py` passes; never stop at direct pin replacement or reuse pre-change review evidence.
8. Run check_workflows.py and the affected unit tests locally. For invocation, additionally require --require-approved FLOW-ID and perform actual per-step runtime checks. A source checker does not execute actions.
9. Save the authorised source to explicitly named staging with immediate target/head reads and SHA/expected-base guards. Preserve unrelated work. Read back every changed source. Leave generated indexes/graph outputs to their owner.
10. Stop at the authorised outcome. Source saving and local tests do not invoke PLAY-0059, PLAY-0056, candidate validation, Actions, merge, external communication or scheduling. Apply those separate authority gates when requested.

Revision rule: changes to the workflow or its dependencies invalidate the old approval. Move affected workflows to needs_review, keep unaffected run evidence and re-review affected behaviour. A new process type does not automatically migrate existing Library records.

## Five-part design checkpoint

Before building the graph in step 4, fill all five parts of Workflows/README.md's mandatory design framework in the template: outcome, necessary work, decisions, recovery and proof. Define observable outcome acceptance first, map every retained operation to a requirement/dependency/risk control, use SKILL-0320 for decision rules and SKILL-0321 for semantic state assessment, specify effect-safe bounded recovery and define the evidence oracle before execution. Use existing workflow-json fields; no unsupported keys or extra phases are required.

In steps 6–7, test the applicable conditions and have the non-author reviewer assess the framework's rejection rule against actual sources/results. An unfilled value, ambiguous predicate, missing evidence or unsupported default blocks approval; authors must not guess values or invent business policy. Preserve manual-versus-enforced and source-versus-runtime distinctions. The existing structural checker does not automatically enforce all five design parts. Changes invalidate affected approval; set needs_review until exact qualification and independent acceptance are renewed.

## Mandatory external-route checkpoint

Before step7 approval, apply SKILL-0313 External execution-route qualification. Record each indispensable effect→exact trigger/ref/SHA and boundary inputs→available callable route→actor/access evidence→observed verification channel→supported alternatives/owner. Read the native trigger and input wiring; enumerate current capabilities. Keep source qualification, current-environment eligibility and actual successful execution distinct. An unresolved required route cannot receive operational-feasibility PASS. Before operational source effects, verify the current route is viable; do not discover a known missing indispensable capability only after writing.

Head must obtain identifiable Guardrail, Reliability and applicable Security findings with source/evidence, actual tested behaviour, disposition and limits; record why any role is not applicable. Loading/pinning a Hat is not its assessment, and multiple roles do not supply non-author independence. Test absent tool, genuine permission denial, skipped trigger, available/unavailable supported alternative, wrong inputs/head/status, partial effects, bounds and terminal re-entry as relevant. Require concrete recovery investigation rather than treating safe refusal as exhausted recovery.

Use existing permitted primitives and raw operator cases for first qualification; do not run an unapproved target or demand whole-workflow success as its own admission prerequisite. An authorised first live use must observe exact triggering and result, and may not claim completion before it. Apply all original authority, frozen-source, shared-budget and independent-review gates; renew affected caller approval after shared guidance changes.

Candidate-validation workflows use the read-only candidate_entry.py assessor through SKILL-0186: entry produces a qualified route plan; validation binds the actual current parent and prepared candidate. Include its native resolver/tests/resources in the exact review. Generic workflows apply the same evidenced-route standard through their own governing Playbook; do not add this candidate-specific helper to unrelated flows. Test strict input refusal and native runner dependency availability, not merely prose phrases.

## Required service-failure cases

Apply SKILL-0313 Service-failure qualification. Required external reads need explicit tested transient/permanent/unknown-effect classification, exact request scope, finite attempts and total/per-request deadlines, bounded pagination and fail-closed exhaustion. Exercise transient-then-success and later-page failure as well as ordinary successful responses. No read result means no absence/pass verdict. Read-only request recovery within a still-incomplete step is distinct from unchanged deterministic candidate reruns; unknown write effects require object verification, not blind retries. Record actual specialist review and retain all existing authority and shared repair bounds.

## Required tracked failure and handback cases

Apply SKILL-0313 Qualify the complete failure feedback loop for qualification cases and PLAY-0069 Mandatory tracked repair and execution handback for the procedure being assessed. Bind actual case inputs, independently expected results, observed packets/effects and exact evidence. Use Workflows/README.md Single-owner rule bindings; do not copy the controller into this authoring checkpoint.

## Source work versus declared operational request

Use SKILL-0313 Existing native control transport and PLAY-0056's exact validation-request contract when applicable. Test a corrected already-staged source tree independently from its intentional same-tree request commit; source-only children never trigger it. Current authority, completed child, relevant reviewed correction, correct failed/validated boundary, complete first-request/failed-tree evidence, exact tree/sole parent/lease/message and original receipt/full-range validation remain mandatory. Do not invent source edits, reset budgets, rerun an unresolved tree or infer execution from a commit. New operational modes require explicit contracts, actual primitive/refusal tests and separate source acceptance before use; absence of one browser/dispatch tool is not proof all native routes are unavailable.

## Mandatory generated visual checkpoint

For every new or revised FLOW, generate its embedded Mermaid visual from its single workflow-json contract using the canonical renderer. Regenerate after contract edits and run the visual parity check before independent review/publication. Missing, stale or duplicate generated visuals fail admission. The visual must show all states, branch labels, post-shared-handler failure destinations, nested calls, waits, the repair/test/review/learning and verified executing-AI handback loop, and only completed success or awaiting_steve service exits. Do not hand-draw a second independent graph or introduce business steps merely for presentation.

Have the non-author reviewer compare meaning and completeness against the actual component/recovery contracts as well as exact structural parity. “100%” visual fidelity means deterministic structural correspondence, not model confidence or proof of runtime success. Runtime results and source qualification remain separate evidence.
